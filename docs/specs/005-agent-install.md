# 005. Установка и обновление кита агентом

Статус: принята
Задачи: T5.9 [ ]
Решения: К15

## Зачем

Пользователь открывает существующий проект, например с кодом Terraform, и говорит агенту: «скачай
и установи кит по этой ссылке». Агент сам решает, какие профили нужны, а когда признаков мало или они
противоречат друг другу, задаёт вопросы. Второй случай: «поставь кит во все проекты в этой папке»,
и у каждого проекта свои профили. Сейчас профили выбирает человек по `install.sh --help`.
Запрос пользователя от 2026-11-12, варианты согласованы по интервью в тот же день.

## Что меняется

### Инструкция для агента `INSTALL.md`

В корне кита появляется `INSTALL.md` на английском (К5: текст для агента). В начале `README.md` —
строка для агента со ссылкой на него. Пользователь может дать ссылку на репозиторий или прямо
на `INSTALL.md`.

Профили выбирает агент по инструкции, а не установщик: так решено (К15). Агент смотрит проект своими
средствами и понимает нюансы, например «провайдер объявлен в модуле или в `root.hcl`». Распознавание
на bash было бы жёстче и сложнее. `install.sh` не меняется.

### Порядок установки по `INSTALL.md`

1. **Где кит.** Если клон есть в `~/projects/platform-agent-kit`, агент делает в нём `git pull` и
   берёт его. Если клона нет, агент предлагает этот путь и спрашивает пользователя. Клонирует по HTTPS
   (`https://github.com/alexwirehead/platform-agent-kit.git`): репозиторий публичный, SSH-ключ не нужен.
2. **Что уже стоит.** Если в проекте есть `.agent-kit.lock`, это обновление: профили из `profiles=`
   остаются в списке. Установщик удаляет профили, которых нет в списке, поэтому агент убирает профиль
   только по прямой просьбе пользователя.
3. **Признаки.** Агент ищет в проекте признаки по таблице «признак → профиль». В таблице есть каждый
   профиль кита, это проверяет тест:

   | Профиль | Признаки |
   |---|---|
   | `terraform` | `*.tf`, `terragrunt.hcl`, `root.hcl` |
   | `yandex-cloud` | провайдер `yandex-cloud/yandex`, SDK `yandexcloud`, `*.yandexcloud.net` |
   | `cloudru` | провайдер `sbercloud-terraform/sbercloud` |
   | `helm` | `Chart.yaml` |
   | `python-exporter` | Python-проект с зависимостью `prometheus-client` |
   | `external-api` | код ходит во внешний API, к которому у агента нет доступа; ставится сам с `yandex-cloud` и `cloudru` |
   | `grafana` | JSON-дашборды Grafana в репозитории |
   | `gitlab-ci` | `.gitlab-ci.yml`, `.gitlab/ci/`, `templates/*.yml` с `spec:inputs` |

4. **Вопросы.** Агент спрашивает пользователя, если: признак слабый (`external-api`, Python без
   экспортера); признаки противоречат друг другу; в Terraform-проекте не видно облака; пользователь
   назвал профиль, признаков которого нет. Для вопросов агент использует инструмент вопросов (Claude
   Code — `AskUserQuestion`, OpenCode — `question`). В вопросе — найденные признаки и предлагаемый список.
5. **Подходящего профиля нет.** Если признаки есть, а профиля под них нет (FluxCD, Ansible), агент
   так и говорит и ставит только ядро и подходящие профили. Правил за кит он не придумывает.
6. **Установка:** `<кит>/install.sh <проект> <профили>`. Нужны `bash`, `git`, `npx`; если `npx`
   нет, агент сообщает об этом и не ставит кит в обход установщика.

### После установки

- **Раздел «Project» в `AGENTS.md`.** Агент заполняет его тем, что видно в проекте: команда полной
  проверки, строки профилей из `project.md`. Чего не видно, агент спрашивает. Плейсхолдер он не
  угадывает.
- **Правила проекта, которые уже были.** Если в `AGENTS.md` вне блока или в `CLAUDE.md` уже есть
  правила агента, агент находит дубли и противоречия с китом. Он предлагает, что убрать, а что
  записать как отступление с причиной. Сам ничего не удаляет.
- **`CLAUDE.md`.** Если `CLAUDE.md` был и в нём нет `@AGENTS.md`, установщик его не трогает, и Claude
  Code не увидит правила кита. Агент предлагает добавить импорт.
- **Итог.** Агент показывает `git status`, поставленные профили с причиной для каждого и то, что
  осталось сделать пользователю. Коммит делает пользователь, агент не коммитит.

### Несколько проектов сразу

Пользователь говорит: «посмотри все директории в `<корень>` и поставь кит». Один репозиторий — один
проект. Профили у разных проектов могут быть разными.

1. **Поиск.** Агент рекурсивно ищет каталоги с `.git`. Внутрь найденного репозитория он не
   спускается, поэтому подмодули и вложенные клоны не попадают в список. Клон самого кита
   пропускается.
2. **Разбор без изменений.** Для каждого репозитория агент выполняет шаги 2–3 порядка установки:
   смотрит lock и признаки. Репозиторий с незакоммиченными изменениями пропускается: иначе изменения
   кита смешаются с работой пользователя. Пользователь может явно включить такой репозиторий.
3. **Один план.** До установки агент показывает одну таблицу: репозиторий, профили, причина, вопрос
   или «пропущен» с причиной. Вопросы о профилях он задаёт одной пачкой, одинаковые объединяет:
   «в 7 Terraform-репозиториях не видно облака — какое?». Ставит после согласия пользователя.
4. **Установка** идёт по репозиториям, клон кита один на все. Если установка в одном репозитории
   упала, агент переходит к следующему, а ошибку записывает в итог.
5. **После установки.** Раздел «Project» агент заполняет тем, что видно. Оставшиеся плейсхолдеры
   и находки по старым правилам агента он не спрашивает по каждому репозиторию, а перечисляет в итоге.
   Итог — таблица: репозиторий, профили, изменённые файлы, что осталось сделать. Агент не коммитит,
   как и для одного проекта.

### Обновление

На «обнови кит» агент выполняет шаги 1–2 и 6 с профилями из `.agent-kit.lock`. Если в ките появились
новые профили и их признаки есть в проекте, агент предлагает их добавить. Добавляет только после
согласия пользователя.

## Что не меняется

- `install.sh`: ни режима `--suggest`, ни распознавания профилей.
- К8: путь к киту по-прежнему любой, `~/projects/platform-agent-kit` — только путь по умолчанию
  для агента.
- Установка руками по `README.md` остаётся как есть.

## Затронутые документы

`README.md` (строка для агента в начале, раздел «Установка в проект»), `docs/00-overview.md`
(раскладка — `INSTALL.md`, К15), `AGENTS.md` кита (правила кита: новый профиль попадает в таблицу
признаков).

## Готово, когда

- Тест: в таблице признаков `INSTALL.md` есть каждый каталог из `profiles/`. Новый профиль без
  строки в таблице роняет тест.
- Тест: `README.md` ссылается на `INSTALL.md`.
- Ручная проверка пользователем: в существующем проекте с Terraform агент по ссылке на кит ставит
  ядро, `terraform` и профиль облака либо спрашивает про облако. В корневой папке с несколькими
  репозиториями разных видов агент показывает один план и пропускает репозиторий с незакоммиченными
  изменениями. Результат записан в заметках задачи.
- `uv run pytest` и ruff проходят.
