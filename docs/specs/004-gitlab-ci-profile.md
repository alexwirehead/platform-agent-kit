# 004. Профиль gitlab-ci: компоненты CI/CD и пайплайны GitLab

Статус: сделана 2026-11-12
Задачи: T4.1 [x]
Решения: К4 (пересмотр), К14

## Зачем

Нужно создавать компоненты CI/CD и пайплайны GitLab, а старые общие шаблоны (`include: project`
плюс `extends: .job`) переводить в компоненты. Главное условие: не переводить в компоненты всё подряд,
а для каждого шаблона сначала оценить, нужен ли компонент вообще. Запрос пользователя от 2026-11-12,
правила собраны по интервью в тот же день (К4) и по документации GitLab (https://docs.gitlab.com/ci/components/,
https://docs.gitlab.com/ci/inputs/, https://docs.gitlab.com/cli/ci/lint/).

## Что меняется

### Профиль `gitlab-ci` вместо заготовки `cicd`

В профиле только GitLab CI, версия GitLab — 18.11. GitHub Actions станет отдельным профилем, когда
появится опыт с ним. К4 пересматривается: заготовка `cicd` заменяется профилем `gitlab-ci`.

### Оценка: нужен ли компонент

Шаблон становится компонентом, только если выполнены все три условия:
- он нужен как минимум в двух проектах (уже сейчас, а не «когда-нибудь»);
- проекты различаются тем, что настраивается через `spec:inputs`, а не копированием и правкой джобов;
- его интерфейс (inputs, имена джобов, stage) стабилен.

Иначе шаблон остаётся локальным: джоб прямо в `.gitlab-ci.yml`, `include: local` или `extends`
внутри проекта. Для каждого шаблона агент выносит один из вердиктов: компонент, оставить локальным,
слить с другим компонентом или удалить. У вердикта есть потребители и причина.

Разросшийся YAML — не повод делать компонент: компонент нужен для повторного использования, а не
для объёма. Объём лечится так:
- логика из `script:` с ветвлениями, циклами или функциями выносится в скрипт в репозитории
  (`.gitlab/ci/scripts/<name>.sh`). Его проверяет shellcheck и можно запустить локально, а в YAML остаётся вызов. Это
  правило действует при любом вердикте;
- большой пайплайн делится на файлы `.gitlab/ci/*.yml` через `include: local`. Это структура, а не повторное
  использование;
- если та же логика нужна в двух и более проектах, она становится компонентом. Скрипт живёт в образе
  компонента, а шаблон остаётся тонким: inputs и вызов. Копии скрипта по проектам не допускаются.

### Рефакторинг старых шаблонов

1. Агент составляет таблицу оценки: шаблон, его потребители, вердикт, причина. Таблица лежит в
   спецификации проекта, который делает рефакторинг.
2. Пользователь согласует таблицу. До этого ни один шаблон не переносится.
3. Каждый шаблон переносится отдельно: релиз компонента, затем перевод потребителей по одному.
   Старый шаблон остаётся под своим тегом, пока у него есть потребители.

### Репозиторий компонента

- У каждого компонента свой репозиторий. По документации GitLab компонент — это
  `templates/<name>.yml` или `templates/<name>/template.yml`, в корне лежит обязательный `README.md`.
  Если у компонента свой образ (Dockerfile, скрипты), используется вариант с каталогом: другим проектам
  отдаётся только `template.yml`.
- Входные параметры объявляются в `spec:inputs` с `description`. Там, где это уместно, задаются `type`,
  `options`, `regex` и `default`.
- Свой образ компонента собирается в том же репозитории: в MR с тегом `:<sha>`, на релизе с тегом
  `:X.Y.Z`. Шаблон ссылается на образ `:X.Y.Z`. Если тег образа в шаблоне не совпал с тегом релиза,
  джоб релиза падает.
- Сборка образа тоже оформляется компонентом (buildah, push в реестр), а не скрытым джобом
  `.build_*` из общего шаблона.

### Тесты и релиз компонента

- `.gitlab-ci.yml` репозитория подключает сам компонент:
  `include: component: $CI_SERVER_FQDN/$CI_PROJECT_PATH/<name>@$CI_COMMIT_SHA`, с inputs на фикстуре
  из `tests/`. Это рекомендуемый способ GitLab, и он проверяет и шаблон, и inputs.
- Релиз выпускается только на тег `X.Y.Z` без `v` (`^[0-9]+\.[0-9]+\.[0-9]+$`): джоб с ключевым
  словом `release` после тестов в пайплайне тега. Именно так GitLab публикует компонент.

### Потребители

Подключение: `include: component: $CI_SERVER_FQDN/<group>/<project>/<name>@<версия>`. Версия
мажорная или минорная (`@1`, `@1.2`): исправления приходят без MR в проект. По документации GitLab
частичные версии работают только с компонентами, опубликованными в CI/CD Catalog. Поэтому каждый
репозиторий компонента — проект каталога: переключатель **CI/CD Catalog project** включён, у проекта
есть описание (у пользователя так и есть, 2026-11-12). Несовместимое изменение inputs или джобов
поднимает мажорную версию.

### Проверки

- Офлайн: `yamllint`, `check-jsonschema --builtin-schema vendor.gitlab-ci` для `.gitlab-ci.yml`,
  `shellcheck` для скриптов `.gitlab/ci/scripts/`. Шаблон `dev/check-ci.sh` запускает их все. Других шаблонов профиль
  не кладёт: скелет репозитория компонента описан примером в навыке.
- `glab ci lint` агент запускает сам, с токеном пользователя, только для чтения (К14). Это
  отступление от правила «агент не ходит в реальную систему»: только линтер GitLab раскрывает
  `include` и проверяет inputs. Пайплайны агент не запускает, переменные CI/CD не читает и не меняет.

### Навык и ревью

- Свой навык `gitlab-ci-components`: оценка, рефакторинг, раскладка репозитория, inputs, тесты, релиз,
  подключение у потребителя, проверки. Сторонних навыков нет.
- Пункты ревью:
  - у нового компонента есть оценка с потребителями и причиной;
  - у каждого input есть `description`;
  - в `script:` нет логики с ветвлениями, циклами или функциями: она в скрипте `.gitlab/ci/scripts/` или в образе
    компонента;
  - тег образа в шаблоне совпадает с тегом релиза;
  - потребитель подключает компонент по версии, а не по ветке или SHA;
  - в шаблонах нет секретов.

## Что не меняется

- Сами компоненты (сборка образа и другие) в кит не входят: это код проектов.
- Не закрепляются правилами: пин сторонних образов по digest, конкретный набор `workflow:rules`,
  `interruptible`. Так решил пользователь.
- GitHub Actions — отдельный профиль в будущем.
- Установщик не меняется.

## Готово, когда

- `install.sh <проект> gitlab-ci` — exit 0, навык и `dev/check-ci.sh` на месте
  (тест `test_every_real_profile`).
- Тест `dev/check-ci.sh`: на корректном `.gitlab-ci.yml` и шаблоне компонента — exit 0, на файле
  с неизвестным ключом джоба — exit 1. Без утилит тест пропускается, как тест Terraform.
- Проверено, как `check-jsonschema` и `yamllint` обрабатывают шаблон компонента с заголовком `spec`
  и разделителем `---`. Результат записан в навыке.
- `uv run pytest` и ruff проходят, shellcheck по шаблону чистый.
