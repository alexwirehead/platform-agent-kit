# 00. Обзор: цель, раскладка, решения

## 1. Цель

Один источник правил и навыков агентов для проектов платформенного инженера. Новый проект получает
обкатанный процесс одной командой, а улучшение правил в ките доходит до всех проектов повторным
запуском установщика.

## 2. Принципы

- Простое лучше сложного: установщик на bash, правила в markdown, без своего CLI. Тому, кто ставит
  кит, нужны только `bash`, `git` и `npx` (для CLI `skills`); тесты кита — на pytest через uv (К10).
- В ките только проверенные правила. Профиль без опыта за плечами остаётся заготовкой, пока правила
  не собраны по интервью с пользователем; правила не выдумываются.
- Сторонний код не хранится в ките: навыки ставятся по ссылке с закреплённым коммитом.
- Проект может отступать от правил кита, но записывает отступление в своём `AGENTS.md` вне
  управляемого блока; файлы кита в проекте не правятся.

## 3. Раскладка

```
core/
  rules.md          фрагмент AGENTS.md: общие правила (EN)
  skills.md         строки таблицы «ситуация → навык» (EN)
  skills.txt        сторонние навыки: URL с коммитом, по одному в строке
  skills/           свои навыки ядра, например change-workflow
  commands/         команды OpenCode: simplify, code-review, security-review
  templates/        docs/specs/README.md, TASKS.md — кладутся, только если их нет
profiles/<имя>/
  README.md         для людей: что даёт профиль (RU)
  rules.md          фрагмент AGENTS.md (EN)
  skills.md         строки таблицы «ситуация → навык» (EN)
  review.md         пункты раздела «Review checks» для команд ревью (EN)
  skills.txt        сторонние навыки профиля
  skills/           свои навыки профиля
  templates/        файлы для проекта, кладутся, только если их нет
  requires          профили, от которых зависит этот
  project.md        строки заготовки раздела проекта в новом AGENTS.md (EN)
install.sh          установщик; install.sh --help — список профилей
INSTALL.md          установка и обновление агентом: признаки профилей, вопросы, несколько проектов (EN)
tests/              pytest: тесты установщика (К10)
pyproject.toml      dev-зависимости: pytest, ruff, shellcheck-py
docs/               обзор и решения (этот файл), спецификации docs/specs/
.devcontainer/      окружение для разработки кита
AGENTS.md           порядок работы над китом; CLAUDE.md импортирует его
TASKS.md            план и статусы задач
```

В проекте после установки:

| Что | Где | В git проекта |
|---|---|---|
| правила ядра и профилей | `AGENTS.md`, блок между `<!-- platform-agent-kit:begin -->` и `:end -->` | да |
| импорт для Claude Code | `CLAUDE.md` с `@AGENTS.md`, если файла нет | да |
| навыки (свои и сторонние) | `.agents/skills/`, симлинки в `.claude/skills/` | нет |
| команды OpenCode | `.opencode/commands/` | да |
| версия кита и профили | `.agent-kit.lock` | да |
| шаблоны процесса | `docs/specs/README.md`, `TASKS.md`, если их нет | да |

## 4. Решения

| № | Решение | Суть |
|---|---|---|
| К1 | Формат (2026-10-24, пользователь) | git-репозиторий и `install.sh`. Не плагин Claude Code (не работает в OpenCode) и не шаблон copier (плохо обновляет готовые проекты) |
| К2 | Инструменты (2026-10-24) | Claude Code и OpenCode из одного источника: `AGENTS.md` общий, `CLAUDE.md` импортирует его |
| К3 | Сторонние навыки (2026-10-24, пользователь) | по ссылке с закреплённым коммитом через CLI `skills` закреплённой версии. Коммит поднимается только после чтения diff навыка |
| К4 | Профили v1 (2026-10-24, пользователь) | ядро, `helm`, `python-exporter`, `external-api`, `yandex-cloud`, `grafana` — обкатаны в работе. `argocd`, `otel`, `monitoring` — заготовки, правила по интервью, у каждой своя спецификация. 2026-11-12: `fluxcd` собран по ADR и скриптам пользователя (К16). Пересмотрено 2026-11-12 (пользователь): заготовка `cicd` заменена профилем `gitlab-ci` (только GitLab, К14); GitHub Actions — отдельный профиль, когда появится опыт |
| К5 | Язык (2026-10-24, пользователь) | для агента (`SKILL.md`, `rules.md`, команды) — английский, в `description` навыка русские ключевые слова для срабатывания. Для людей (README, спецификации, решения, `TASKS.md`) — русский. Ядро требует от агента писать документы и коммиты проекта по-русски |
| К6 | Подход к доработкам (2026-10-24, пользователь) | часть ядра: спецификация → задача → тест → код, статусы задач, ветки `feature/NNN-slug`, мерж `--no-ff` после проверки пользователем. Процедура — навык `change-workflow`, шаблоны — `core/templates/` |
| К7 | Сборка `AGENTS.md` (2026-10-24) | управляемый блок между маркерами: ядро, затем профили в порядке аргументов, затем общая таблица «ситуация → навык». Повторный запуск заменяет только блок |
| К8 | Где лежит кит (2026-10-24, пересмотрено 2026-10-24, пользователь) | обычный клон репозитория в любом каталоге, например `~/projects/platform-agent-kit`; путь не закреплён, `install.sh` находит свой каталог сам. Было: `~/.agents/platform-agent-kit` — скрытый каталог для проекта неудобен |
| К9 | Сообщения коммитов (2026-10-24, пользователь) | Conventional Commits 1.0.0 (https://www.conventionalcommits.org/en/v1.0.0/): `<type>(<scope>): <описание>`. Тип на английском: `feat` и `fix` обязательны по спецификации, остальные из списка commitlint (`build`, `chore`, `ci`, `docs`, `style`, `refactor`, `perf`, `test`). Scope — область кода (в ките `core`, `install`, профиль). Описание и тело на русском, номер задачи — футер `Задача: T2.2`, несовместимое изменение — `!` перед двоеточием и футер `BREAKING CHANGE:`. Merge-коммит в том же формате, в теле ссылка на спецификацию |
| К10 | Тесты кита (2026-10-24, пользователь) | pytest через uv вместо тестов на bash: писать их на shell слишком тяжело. Dev-зависимости в `pyproject.toml`: `pytest`, `ruff`, `shellcheck-py`. Установщик остаётся на bash, чтобы ставящему не нужен был Python |
| К11 | Удалённый репозиторий (2026-10-24, пользователь) | `git@github.com:alexwirehead/platform-agent-kit.git`, remote `origin`. Пушатся все ветки; `main` меняется только мержем по правилам веток |
| К12 | Кит на своих правилах (2026-10-24, пользователь) | кит ставит в себя своё ядро без профилей (`./install.sh .`): блок `AGENTS.md`, навыки, команды. Отступление — язык по К5. `.agent-kit.lock` кита не коммитится. Спецификация `docs/specs/002-kit-self-install.md` |
| К13 | Terraform и Terragrunt (2026-11-03, пользователь, интервью) | профиль `terraform` — общие правила, факты провайдеров в `yandex-cloud` и новом `cloudru` (Cloud.ru Advanced). Terraform CLI и Terragrunt 1.x; свой репозиторий у каждого модуля (semver-теги) и live-репозиторий у каждого облака (`<каталог>/<компонент>/` в корне); готовые модули — только из зеркала во внутреннем GitLab; в модуле только нижние границы версий; провайдеры из зеркала, lock в git; state — `s3` с `use_lockfile`; агент только офлайн; проверки fmt, validate, tflint, trivy, terraform-docs; навыки terrashark, `terraform-style-guide`, `refactor-module`. Спецификация `docs/specs/003-terraform-profile.md` |
| К14 | GitLab CI (2026-11-12, пользователь, интервью) | профиль `gitlab-ci`, GitLab 18.11. Компонент — только если шаблон нужен в двух и более проектах сейчас, различия укладываются в `spec:inputs` и интерфейс стабилен; иначе шаблон локальный. Разросшийся YAML — не повод: логика в `.gitlab/ci/scripts/`, пайплайн делится на `.gitlab/ci/*.yml`. Рефакторинг старых шаблонов — таблица оценки, согласование, перенос по одному. Свой репозиторий у каждого компонента, проект CI/CD Catalog, свой образ `:X.Y.Z` в нём же, самоподключение на `$CI_COMMIT_SHA`, релиз на тег `X.Y.Z` джобом `release`; потребитель — `@1` или `@1.2`. Агент сам запускает `glab ci lint` (только чтение) — отступление от правила «агент не ходит в реальную систему». Спецификация `docs/specs/004-gitlab-ci-profile.md` |
| К15 | Установка агентом (2026-11-12, пользователь, интервью) | профили выбирает агент по `INSTALL.md` (таблица «признак → профиль», когда спрашивать), а не `install.sh --suggest`: агент понимает нюансы, распознавание на bash было бы жёстче и сложнее. Клон — `~/projects/platform-agent-kit` (`git pull`), иначе вопрос; по HTTPS. Профили из `.agent-kit.lock` сохраняются. Несколько проектов: рекурсивный поиск репозиториев, грязные пропускаются, один план, вопросы пачкой. Агент не коммитит. Спецификация `docs/specs/005-agent-install.md` |
| К16 | Flux (2026-11-12, пользователь, интервью и ADR) | профиль `fluxcd`: Flux Operator и `FluxInstance` с `multitenant: true`, bootstrap через Terraform; fleet- и components-репозитории, гибрид ControlPlane D1/D2 — `GitRepository` на компонент, версии `<COMPONENT>_REF` в `environments/<env>/versions.yaml` без значений по умолчанию, вне dev-среды платформы только защищённые теги; сервис — файл `ResourceSetInputProvider`; агент офлайн; проверки — обобщённые скрипты пользователя; навыки `gitops-knowledge`, `gitops-repo-audit`. Профиль `fluxcd-debug` (по желанию, агент спрашивает при установке): `gitops-cluster-debug` только через `flux-operator-mcp serve --read-only` — отступление от правила «агент не ходит в реальную систему», кластер агент не меняет. Доставка секретов, change gates, перенос с Argo CD — не в ките. Спецификация `docs/specs/006-fluxcd-profile.md` |
| К17 | Навыки после сжатия контекста (2026-11-13, пользователь) | порядок этапов `change-workflow` записан и в правиле 7 ядра: блок `AGENTS.md` переживает сжатие контекста, а загруженный навык — нет (OpenCode). Навык загружают снова, если его текста уже нет в контексте. Плагин-сторож и «Этап:» в ответах отложены, пока текстовой правки хватает. Спецификация `docs/specs/007-workflow-after-compaction.md` |
