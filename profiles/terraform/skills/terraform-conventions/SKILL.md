# Terraform and Terragrunt conventions

Runtime: Terraform CLI and Terragrunt 1.x, not OpenTofu. Cloud specifics (provider, mirror address,
backend endpoint) come from the facts of the cloud profile (`yc-fact-check`, `cloudru-fact-check`),
Terraform and Terragrunt syntax — from the official docs (`source-driven-development`), never from memory.

## The agent works offline

Allowed: `terraform fmt`, `terraform init -backend=false`, `terraform validate`, `tflint`, `trivy config`,
`terraform-docs`, `terragrunt hcl fmt`, `terragrunt hcl validate`, `dev/check-terraform.sh`.

Never: `plan`, `apply`, `destroy`, `import`, `state`, `output`, `refresh`, any `terragrunt run`
(it initialises the backend and reads dependency outputs). Never ask for keys or tokens. If a change needs
a real plan, ask the user to run it and paste the relevant part with secrets removed.

## Repositories

Every module has its own repository; every cloud has its own live repository. There is no monorepo.
Never committed: `.terraform/`, `.terragrunt-cache/`, `*.tfstate*`, `*.tfplan`, generated `backend.tf`
and `provider.tf`.

### Module repository

```
terraform.tf     required_version and required_providers
variables.tf     every variable has description and type; secrets have sensitive = true
main.tf          resources and data sources
locals.tf        optional
outputs.tf       every output has description; secrets have sensitive = true
README.md        generated by terraform-docs, never edited between its markers by hand
CHANGELOG.md     one section per release
.tflint.hcl      kit template
```

- No `provider` and no `backend` blocks: Terragrunt generates them in the live repository.
- Versions are lower bounds only: `required_version = ">= X.Y"`, providers `version = ">= X.Y"`. The
  exact version is chosen by the live repository and its lock file.
- `.terraform.lock.hcl` is not committed: the lock file belongs to the root configuration.
- Release is a semver tag `vX.Y.Z` with a `CHANGELOG.md` section:
  - MAJOR — a required input added, an input or output removed or renamed, a resource replaced or its
    address changed without a `moved` block;
  - MINOR — an optional input or a new output, a new resource behind a default-off flag;
  - PATCH — a fix with no change of the interface and no replacement.
- Identity: `for_each` over stable keys, `count` only as a 0/1 toggle, never a list index as identity.

### Live repository

```
root.hcl                       backend and provider generation, shared locals
<folder|project>/
  folder.hcl                   locals of the level: folder or project ID, names
  <component>/terragrunt.hcl   one unit = one module call = one state
```

There is no `live/` directory: levels start at the repository root. Real cloud, folder and project IDs
are configuration and live in `*.hcl`; keys, tokens and passwords never do.

`root.hcl` generates the backend with a plain `generate` block, not `remote_state`: for the `s3` backend
`remote_state` makes Terragrunt manage the bucket (create it, turn on versioning) with AWS-specific calls.
The bucket is created once outside Terragrunt, with versioning on.

```hcl
# root.hcl — endpoint and the cloud-specific skip_* flags come from the cloud facts
generate "backend" {
  path      = "backend.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
terraform {
  backend "s3" {
    bucket       = "<state-bucket>"
    key          = "${path_relative_to_include()}/terraform.tfstate"
    use_lockfile = true
    # endpoints, region, skip_* — from the cloud facts
  }
}
EOF
}

generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<EOF
terraform {
  required_version = "= <terraform version>"
  required_providers {
    <name> = {
      source  = "<namespace>/<name>"
      version = "= <provider version>"
    }
  }
}
provider "<name>" {
  # settings from locals; credentials only from the environment
}
EOF
}
```

`dynamodb_table` is never used: the S3 backend deprecates DynamoDB locking.

```hcl
# <folder>/<component>/terragrunt.hcl
include "root" {
  path = find_in_parent_folders("root.hcl")
}

terraform {
  source = "git::https://<gitlab>/<group>/<module>.git?ref=v1.4.0"
}

dependency "vpc" {
  config_path = "../vpc"

  mock_outputs                            = { network_id = "mock-network-id" }
  mock_outputs_allowed_terraform_commands = ["validate"]
}

inputs = {
  network_id = dependency.vpc.outputs.network_id
}
```

- `source` is always a module repository in the internal GitLab with a tag in `ref`, never a branch,
  a public GitHub URL or a registry address. A ready-made module is used only from its GitLab mirror;
  read its variables and resources at that tag before use.
- Moving an environment to a new module version is its own change of `ref`, rolled out from the least
  critical environment up. Read the module `CHANGELOG.md` between the two tags first.
- The provider lock file `.terraform.lock.hcl` of each unit is committed with hashes for `linux_amd64`
  and `darwin_arm64`. It is updated by a human or CI with `providers lock` against the mirror (command in
  the cloud facts), not by the agent.

## Changes that destroy or replace

- Renamed resource or module call inside one state — a `moved` block in the same change.
- Resource moved to another unit (another state) — `removed { from = ...; lifecycle { destroy = false } }`
  in the old unit and `import { to = ...; id = ... }` in the new one; the user applies the old unit first.
- Any replacement or destroy in a plan is named in the change description with the reason and the
  rollback path.

## Secrets

- No secret values in code, `*.tfvars`, `inputs` or defaults; secret variables and outputs have
  `sensitive = true`.
- The state holds secrets in plain text: never print it, never commit it, keep the bucket private.
- Prefer ephemeral resources and write-only attributes when the provider has them (`terraform-style-guide`).
- How secrets are delivered (SOPS, Vault) is a project decision, written in the project section of
  `AGENTS.md`.

## Checks

`dev/check-terraform.sh` before every commit. In a module repository: `terraform fmt -check`,
`init -backend=false` and `validate`, `tflint` (`.tflint.hcl`, preset `all`), `trivy config` (HIGH and
CRITICAL fail), README up to date with `terraform-docs`. In a live repository: `terragrunt hcl fmt --check`
and `terragrunt hcl validate`; full validation of units happens in CI together with the plan.

Delivery: plan on a merge request, apply only of the reviewed plan and only from `main`. The pipeline
itself belongs to the project's CI rules.
